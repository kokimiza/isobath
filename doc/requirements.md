# 1. 目的とスコープ

## 1.1 目的

ISOBATHは、人間をあらかじめ決められた性格タイプへ分類しない。

独自に設計した観測項目群への回答を継続的に集め、その統計的な分布から、人格に関連する潜在構造・個人差・時系列変化を探索的に可視化する。これを「人格海図」と呼ぶ。

研究としての問いは、**「人の回答傾向は、データが増えるといくつのまとまりとして現れ、その数は安定するのか」**である。固定タイプを作ることは目的ではない。まとまりの数・特徴・境界が観測の蓄積に対してどこまで再現するかを明らかにすることが目的であり、**「明確な群がない」「細分化が続く」という結果も成果として扱う**（仮説と検証手続きは [statistics.md](statistics.md) §0）。

利用者は診断される対象ではなく、海図をつくる観測点の一つとして参加する。

## 1.2 位置付け

- ISOBATHは、既存の人格診断尺度を代替するものではない。
- 臨床的・心理学的に確立された尺度であるとは主張しない。
- 医療診断、精神疾患の診断、能力評価、採用適性の判定、人間の優劣判定を目的としない。
- 生成AIによる人格判定を中核機能にしない。結果がどのような計算で得られたかを説明できることを優先する。

## 1.3 MVPのスコープ

MVPは、**planned missing design による初期調査（Pilot Phase 1）を公開サービスとして実施し、観測の蓄積に応じて海図の形を定めていくこと**を範囲とする。人数によって処理を切り替えず、最初の1人から同じモデルで海図を更新する（§4、[statistics.md](statistics.md)）。

| 区分 | MVPに含む | MVPに含まない（LATER） |
|---|---|---|
| アカウント | 登録、ログイン、ログアウト、アカウント削除 | — |
| 測深 | 初回測深、継続測深、セッション、バッチ回答、中断からの再開 | Adaptive出題（Phase 2・3） |
| 項目 | 独自の候補項目群、共通アンカー、ブロック割当、品質確認項目 | Cognitive Tasks、Behavioral Tasks |
| 統計（オフライン） | 項目分析、ベイズ順序尺度・因子混合モデルの推定（[statistics.md](statistics.md)）、群数と分割の事後分布 | 別のモデル族との比較（CFA、LPA、階層的クラスタリング、Spectral、Multi-model Consensus）、未踏域検出 |
| 統計（オンライン） | 確定した成果物のもとでの位置の事後計算 | 再測定データが揃うまでDrift判定を行わない |

# 2. 用語

| 用語 | 定義 |
|---|---|
| 測深 | 質問への回答による観測 |
| 初回測深（Initial Survey） | 登録直後に行う約100問の観測 |
| 継続測深（Continuous Survey） | ログイン時などに行う10〜20問の追加観測 |
| 観測項目 | 質問 |
| 観測点 | 利用者 |
| 現在地（Position） | 海図の座標系における利用者の推定位置 |
| 推定精度（Confidence） | 現在地の推定の確からしさ。標準誤差から算出する |
| 海域（Region） | クラスタ |
| 所属確率（Membership） | 利用者が各海域に属する確率 |
| 航跡（Journey） | 現在地の時系列 |
| Drift | 測定誤差を超える、継続的な現在地の変化 |
| 海図（Chart） | 集約された密度・等値線・海域の成果物。版で管理する |
| 群数 | 3つを区別する。`K`（母集団の成分数）、`T_N`（この標本で埋まった成分数）、`T̂`（代表分割の海域数）。表示と判定に使うのは `T_N`（statistics.md §6.4） |
| 代表分割 | 事後の分割の集合から、固定した損失規則で選ぶ一つの分割（statistics.md §6.1） |
| 未踏域（UNSURVEYED） | 既存の海図では説明しにくい観測点 |
| 観測領域 | 質問を漏れなく作るための設計上の区分（D01〜D16）。モデルでは因子の事前構造として使う（ST-ITM-03） |
| 共通アンカー | 全参加者が回答する項目 |
| ブロック | アンカー以外の候補項目を分けた出題単位 |
| Item Set Version | 質問項目群の版 |
| linking items | Item Set Versionの間で維持する共通項目 |
| 共回答数 | ある項目ペアの両方に回答した人数 |

> 用語の整理：concept.md では、海図の初期状態と外れ値の扱いの両方に「UNSURVEYED」が使われていた。本書では外れ値だけを **UNSURVEYED（未踏域）** と呼ぶ。人数のしきい値による海図段階（UNCHARTED / PRE-CHART / PROTO / SEED / CHART 1.0）は §4 のとおり廃止した。

# 3. 利用者と利用シナリオ

## 3.1 利用者

| 利用者 | 説明 |
|---|---|
| 観測参加者 | 一般利用者。測深に回答し、自分の現在地・航跡・海図を閲覧する |
| 未登録訪問者 | ランディングページと公開海図を閲覧する |
| 運営者 | 項目の管理、海図の再計算と公開、Emergency Modeの操作を行う |

## 3.2 主要シナリオ

**S1. 初期測量隊として参加する（観測がまだ少ない時期）**

1. ランディングページで、海図がまだ形成中であることを知る。
2. 登録し、同意事項（§10.1）に同意する。
3. 初回測深（約100問）に回答する。途中で中断し、後日再開できる。
4. 完了後、回答を受け付けたことと、翌日 01:00 の日次更新で反映されることが表示される。
5. 次にログインしたとき、自分の観測番号・参加人数と、自分の現在地を見る。このときの信用楕円は非常に大きく、「まだほとんど分かっていない」ことがそのまま見える。公開の密度図は、人数が k 未満のセルを出さない規則（FR-CHT-04）により、まだ空である。

**S2. 観測が集まり、海図の形が定まっていく**

1. 参加者が増えるにつれ、同じ処理のまま事後分布が狭まる。信用楕円が小さくなり、公開の密度図にセルが現れる。
2. 群数の事後分布が複数群を支持するようになると、海域と所属確率が表示される（FR-UNC-03）。
3. 不確実性が大きい間は「暫定海図であり、大きく改訂される可能性がある」ことが明示される（FR-UNC-05）。

**S3. 継続して観測する**

1. ログイン時に、10〜20問の継続測深が提示される。
2. 回答は、その日の締め（01:00）の後の日次更新で現在地の再推定に使われ、航跡に記録される。
3. 海図が改訂された場合、CHART UPDATE として、自分の変化（PERSONAL UPDATE）とは区別して通知される。

**S4. 退会する**

1. 設定画面からアカウントを削除する。
2. 本人のデータは削除され、次回の日次更新から海図に含まれなくなる（§10.3）。

# 4. 海図の形成と不確実性

海図は観測の蓄積に応じて形が定まっていく。**収集している過程そのものをサービスの成長過程として見せる。** ただし、その過程を人数のしきい値で区切らない。

処理は人数によらず常に同じである（[statistics.md](statistics.md)）。

    全回答 → ベイズ順序尺度・因子混合モデル → 位置・所属確率・群数の推定 → 海図

回答者が1人でも100万人でも、**生成モデル・推定対象・意思決定規則**は変わらない。人数が変われば事後分布は変わる（広さだけでなく、中心・形・峰の数・代表分割も変わる）。変えないのは「何を仮定し、何を推定し、どう決めるか」である。群の数は解釈したい量であるため、成分数そのものに事前分布を置く（MFM。statistics.md §2.2）。

| ID | 要求 | レベル |
|---|---|---|
| FR-UNC-01 | 人数のしきい値によって、機能の有無や処理の内容を切り替えないこと | MUST |
| FR-UNC-02 | 位置・所属・海図を示すときは、事後の不確実性を必ず併記すること。不確実性を隠さない | MUST |
| FR-UNC-03 | 海域（群）の表示は、標本内の群数の事後分布が複数群を支持し、かつ代表分割が2つ以上の海域を持つときに限ること。支持しないときは「まだ群として分かれていない」と示すこと。判定の式は statistics.md §9.3 で定める | MUST |
| FR-UNC-04 | 標本内の群数の事後分布 `P(T_N=t)` と、代表分割の確からしさ（credible ball の半径）を公開すること。母集団の成分数 `K` と、代表分割の海域数 `T̂` を混同させない表示にすること（statistics.md §6.4） | MUST |
| FR-UNC-05 | 不確実性が大きい間は「暫定海図」と表示すること。「人類の海図」とは呼ばないこと | MUST |
| FR-UNC-06 | モデルの改訂は自動では行わないこと。運営者が診断値（statistics.md §4.3）とレポートをレビューして承認し、**承認後の最初の日次更新（§4.1）の時点で有効になる**こと。日中に画面上の版が変わらないこと | MUST |
| FR-UNC-07 | 収束診断（statistics.md §4.3）を満たさない推定結果から成果物を作らないこと | MUST |

- 人数のしきい値による海図段階（UNCHARTED 〜299 / PRE-CHART 300〜 / PROTO 500〜 / SEED 1,000〜 / CHART 1.0）は廃止した。段階ごとに統計手法と表示を切り替える設計をやめ、一つのモデルと不確実性の表示に置き換えた。
- DBとAPIの `stage` は、成果物があるかどうかを表す2値（`COLLECTING` / `CHARTED`）に縮小する。
- 「未測量」「測量船」などの語は、世界観の表現として画面の文言に使ってよい。機能の分岐条件には使わない。

## 4.1 日次更新（締めとバッチ）

**海図と現在地は、回答した時点では更新しない。毎日 01:00（日本時間）に開始する日次バッチで一括して更新する。** 参加人数（初回測深の完了者数）は集計値であり、完了の時点で反映する。 利用者は、次にログインしたときに更新後の結果を確認する。

    締め区間 D（例：9/21 分）

    9/20 01:00:00.000 JST  ──────────────►  9/21 00:59:59.999 JST
    │                                              │
    └── この間に「完了」したセッションが対象 ────────┘
                                                   ▼
                                         9/21 01:00 日次バッチ開始
                                         （01:00:00 以降の完了は 9/22 分）

| ID | 要求 | レベル |
|---|---|---|
| FR-BAT-01 | 海図（密度・等値線・集計値）と利用者の現在地は、日次バッチでのみ更新すること。回答・完了の時点では更新しない。参加人数は完了の時点で反映する | MUST |
| FR-BAT-02 | 締め時刻は毎日 01:00:00 JST（16:00 UTC）とし、締め区間は「前日 01:00:00 JST 以上、当日 01:00:00 JST 未満」とする。日次バッチは締め時刻の後（01:07 JST）に起動し、取りこぼしに備えて 01:37 JST にも起動する。起動が遅れても、対象は締め時刻で決まる（FR-BAT-03） | MUST |
| FR-BAT-03 | セッションがどの締め区間に属するかは、**サーバが記録した完了時刻（`completed_at`）**で決めること。バッチの開始の遅れ、実行時間、再実行によって、対象となるデータが変わらないこと | MUST |
| FR-BAT-04 | 未完了のセッションの回答は、どの締め区間の対象にもしないこと | MUST |
| FR-BAT-05 | 日次バッチは次を行うこと。<br>(1) その締め時刻の時点で有効なモデルの版を決める<br>(2) 締め時刻までに完了したセッションの回答を使い、対象者の現在地を推定して保存する<br>(3) 研究参加者の現在地から、海図（密度・等値線・集計値）を生成する<br>(4) 参加人数などの統計を集計する<br>(5) 実行の記録（締め時刻、版、件数、成否）を残す | MUST |
| FR-BAT-06 | 同じ締め時刻でバッチを再実行しても、結果が重複・変化しないこと（冪等性） | MUST |
| FR-BAT-07 | バッチが失敗した日、または起動されなかった日は、前回成功した結果を表示し続けること。その締め区間のデータは、次に成功したバッチで反映すること（海図と現在地は累積のデータから作るため、欠けた日の分も失われない） | MUST |
| FR-BAT-11 | 起動の取りこぼしに備えて、同じ締め時刻に対するバッチを締め時刻の後に複数回起動してよい。成功済みの締め時刻に対する起動は、何もせずに終了すること | MUST |
| FR-BAT-08 | 研究参加の撤回とアカウント削除は、次の日次バッチで生成する海図から除外すること。モデル（因子負荷・海域）の推定し直しは、次のモデル改訂で行う | MUST |
| FR-BAT-09 | バッチの失敗・遅延を検知し、運営者に通知すること | MUST |
| FR-BAT-10 | 設定値によって、日次バッチを停止できること（Emergency Mode） | MUST |

## 5.5 航跡と変化

| ID | 要求 | レベル |
|---|---|---|
| FR-JNY-01 | 日次更新で現在地を推定するたびにスナップショットを保存し、航跡として時系列で表示すること | MUST |
| FR-JNY-02 | 本人の変化（PERSONAL UPDATE）と海図の改訂（CHART UPDATE）を、別のイベントとして区別して表示すること | MUST |

## 6.4 データ品質

| ID | 要求 | レベル |

| ST-QLT-02 | 品質フラグから、セッションごとにデータ品質スコア（`data_quality_score`）を算出すること。心理測定の「信頼性」と混同しない名前にする | MUST |
| ST-QLT-03 | 低品質の回答は削除しない。Raw Observation → Quality Flag → Validated Dataset のように、分析用データセットから除外する | MUST |

## 6.5 海図の生成（オフライン）

| ID | 要求 | レベル |
|---|---|---|
| ST-CHT-01 | 再計算はHTTPリクエストから実行しないこと | MUST |
| ST-CHT-02 | パイプラインは次の順で行う。<br>品質フィルタ → 項目分析のレポート → 事前予測検査 → MCMC（statistics.md §4.2）→ 収束診断 → 尺度の標準化と前の版への整列 → 代表分割と海域IDの継承 → 密度の生成 | MUST |
| ST-CHT-03 | 比較尺度の回答（ST-EXT-01）は、海図の学習データに含めないこと | MUST |
| ST-CHT-04 | アカウント削除の tombstone があるユーザーを学習データから除外すること | MUST |
| ST-CHT-05 | 各版について、使用したデータの件数、Item Set Version、パイプラインのコードの版、乱数シード、収束診断の値を metadata に記録し、再現できるようにすること | MUST |
| ST-CHT-06 | 射影を初回から固定し、経年比較には測定モデル・中心・尺度を含む参照成果物を固定すること（statistics.md §5）。Procrustesだけで版間の測定尺度の同等性を主張しない | MUST |
| ST-CHT-07 | 海域には、版をまたいで同じ海域を指す region_lineage_id を付けること。対応付けは、共有する観測者の重なりと Hungarian法で行う（statistics.md §5.5）。これがないと、利用者の所属海域が更新ごとに別物になる | MUST |
| ST-CHT-08 | 海域の分割・統合を lineage のイベントとして記録すること | LATER |
| ST-CHT-09 | 別のモデル族との比較（CFA、LPA、階層的クラスタリング、Spectral、Multi-model Consensus）、未踏域の検出 | LATER |

## 6.6 現在地の推定（オンライン）

| ID | 要求 | レベル |
|---|---|---|
| ST-POS-01 | 現在地は、日次バッチの中で、その時点で有効な成果物（保存した事後ドロー）のもとでの事後計算だけで算出すること（statistics.md §7.1）。APIのリクエスト処理では算出しない。モデルの推定もしない | MUST |
| ST-POS-02 | 一部の項目にしか回答していない利用者でも、現在地を推定できること。未回答の項目は尤度に現れないだけで、補完しないこと | MUST |
| ST-POS-03 | 現在地と一緒に事後標準偏差と95%信用領域を算出し、2次元ドローを保存すること。全員にグリッドHPD近似を用い、楕円を補助表示する場合も経験的確率質量を校正する（statistics.md §6.3） | MUST |
| ST-POS-04 | 現在地の推定には、各項目の最新の回答を使うこと | MUST |
| ST-POS-05 | 所属確率は、事後ドローごとに代表海域へ対応づけた所属の頻度として算出すること。成分ラベルに依存せず、事象が排他的であること。どの海域にも対応づかない確率（`unmatched`）も返すこと（statistics.md §6.2） | MUST |

## 6.7 Drift

| ID | 要求 | レベル |
|---|---|---|
| ST-DRF-01 | 座標の単純な距離でDriftと判定しないこと | MUST |
| ST-DRF-02 | 再検査信頼性 r は、ISOBATHの再測定データ（FR-CON-02 (b)）から推定すること。文献値は使わない | MUST |
| ST-DRF-03 | r が推定できるまで、Drift判定を行わないこと | MUST |
| ST-DRF-04 | Drift判定の基準は Reliable Change（Sdiff = SD × √(2(1−r))）とし、測定誤差を超える同じ方向の変化が3セッション続いたときに初めてDriftと認定すること | SHOULD |
| ST-DRF-05 | 誤差共分散を考慮した多次元の判定（D² = Δ'ΣΔ⁻¹Δ）、および事後分布から直接「変化が起きた確率」を出す判定への置き換え | LATER |
| ST-DRF-06 | 等化していない Item Set Version をまたいで、Drift判定をしないこと | MUST |

## 6.8 研究設計の検証

| ID | 要求 | レベル |
|---|---|---|
| ST-RES-01 | 主仮説（群構造の安定化）と対立仮説（連続的な個人差、階層的な構造）を、同じデータに対する予測性能と再現性で比較すること（statistics.md §0.1） | MUST |
| ST-RES-02 | 標本サイズの影響は、**同じ期間・同じ項目版のデータから作った入れ子の無作為標本**で評価すること。日々の海図更新の履歴を、人数の効果の根拠に使わないこと（人数の増加と利用者層の変化が混ざるため） | MUST |
| ST-RES-03 | 群プロフィールの再現性は、独立したホールドアウト標本で評価すること | MUST |
| ST-RES-04 | 「人数が増えれば真のタイプ数に収束する」を前提にしないこと。モデルの誤指定だけでも成分数はデータ量とともに増えうる。安定性は経験的に測る対象として扱い、公開文書にもその旨を書くこと | MUST |
| ST-RES-05 | 希少な群を報告するときは、品質スコア・回答時期・外れ値指標を併記し、低品質の回答や特定時期の流入で構成されていないことを確認すること | MUST |
| ST-RES-06 | 同じ人の繰り返し回答を研究に使う場合は、個人内変動を扱う縦断モデルを用いること。それまでは、繰り返し回答を「最新の位置の推定精度を上げるもの」として扱い、個人の変化を主張しないこと | MUST（縦断モデルはLATER） |

| ST-EXT-02 | 比較尺度は、独自の軸の解釈（外的妥当性の検討）だけに使うこと。利用者の画面に既存の類型名を表示しない | MUST |

    POST /v1/me/surveys/{id}/answers
    {
      "answers": [
        {"question_id": 14, "value": 4, "response_ms": 3120},
        {"question_id": 27, "value": 2, "response_ms": 2480}
      ]
    }

現在地レスポンスの例：

    {
      "chart": {"version": "2027.03", "stage": "CHARTED"},
      "position": [0.31, -0.82],
      "se": [0.12, 0.15],
      "confidence": 0.81,
      "regions": [

海域を表示する条件（FR-UNC-03）を満たさないときは `regions` を返さない。成果物がないとき（`stage = COLLECTING`）は、`position` の代わりに `observer_number` を返す。

      "next_update_at": "2027-03-15T16:00:00Z"   // 次回の締め時刻
    }

## 8.3 海図の成果物

日次バッチが生成した海図（密度のグリッド、等値線、集計値）は、データベースに保存し、`GET /v1/chart/current` で配信する。

- 集計済みの小さなJSON（20 KB 未満）とする。利用者の個別座標を含めない。
- `Cache-Control: public, max-age=<次の締め時刻までの秒数>` を返し、Cloudflare でキャッシュする。1日に1回しか変わらないため、API への負荷はほぼ一定になる。

# 12. MVPの受け入れ基準

1. 新規利用者が登録と同意を済ませ、初回測深の約100問を中断・再開しながら完了できる。
2. 出題が planned missing design（アンカー30問、層化したブロック、品質確認項目）に従い、出題の記録がセッションごとに残る。
3. 割り当てられていない項目への回答、二重回答、値域外の値が、API と DB の両方で拒否される。
4. 他の利用者のデータを、API からも、FastAPI の実装を迂回したDBクエリからも取得できない（RLS の検証テスト）。
5. オフラインのパイプラインが、Supabase のデータから、品質フィルタと欠損を含む推定を経て、版付きのモデルと海図を再現可能に出力する。収束診断を満たさないときは、成果物を作らずに失敗する。
6. SBC で推論実装の校正を確認できており、合成データからの回復を反復して測れている（statistics.md §9.1、§9.2）。回答者が1人でもエラーにならず、本人の位置の事後が事前より狭くなる。
7. 現在地と信用楕円が表示される。海域と所属確率は、群数の事後分布が複数群を支持するときだけ表示される。どの場合も断定的な表現を使わない。
8. アカウントを削除すると、本人のデータが消え、tombstone によって次の再計算から除外される。
9. Emergency Mode の各レベルで、期待したとおりに機能が止まる。API が止まっても、静的な画面は表示される。
10. `onrender.com` への直接アクセスが 404 になる。
11. 00:59 に完了したセッションは当日の日次更新に、01:00 に完了したセッションは翌日の日次更新に反映される。同じ締め時刻でバッチを再実行しても結果が変わらない。
