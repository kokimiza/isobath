# 研究データ管理規程（内部）

> リーガルレビュー（2026-09-21）反映済み。【要記入】を確定して施行する。

版：0.1

### 2026-09-23追補：研究専用属性

出生年・月と本人が回答する現在の性別を `app.research_demographics` に分離する。API・日次バッチ・利用者ロールへSELECTを付与しない。解析担当には版2の研究同意が有効な人だけを返す `analysis.research_demographics` を許可する。入力は登録時に取得するが、不同意・撤回時は非公開保管のみとし研究に使わない。アカウント削除でカスケード削除する。訂正・属性のみの削除請求は本人確認のうえ管理担当が専用テーブルで対応し、既存の解析複製にも反映する。

性別の「回答したくない」や既存ユーザーの未入力を補完しない。出生「日」を取得しない。年齢は解析カットオフの先月末（日本時間）基準で導出する。`statistics.md §12.1` の補助回帰以外（海図推定・個人位置・設問選択・広告・個人評価）に使わない。出生年月や性別をログ・エラー・公開成果物へ出力しない。少数区分を公表せず、非公開係数レポートもそのまま公表しない。研究説明書とプライバシーポリシーの版2を公開し、再同意を得てから解析する。

仮名化、アクセス権、保存期間、削除、研究終了後の扱い、公表時の匿名化を定める。

## 1. データの区分

| 区分 | 例 | 格納先 | 性質 |
|---|---|---|---|
| A. 本人識別情報 | メールアドレス、認証情報 | `auth.users`（Supabase Auth） | 個人情報 |
| B. 対応表 | `user_id` ↔ `pseudo_id` | `app.profiles` | 個人情報（再識別の鍵） |
| C. 分離された研究データ | `pseudo_id` と回答・回答日時・回答時間・推定結果・品質指標（研究参加者のみ） | `analysis.responses`（ビュー） | **通常の個人データ**として扱う。法定の「仮名加工情報」制度は用いない |
| D. 集計データ | 公開される人格海図、論文の統計値 | `static/charts/`、論文等 | 個人を特定できない情報 |

「匿名化」という語は用いない。B を破棄しても、他の保有情報との容易な照合可能性等を検討するまでは、C を個人データとして扱い続ける。

## 2. 質問票の分類（項目追加時の必須手続）

質問項目を追加・変更するときは、各項目を次のいずれかに分類し、`app/items/items-*.csv` の `screening` 列（`normal` / `caution`）に記録する。`caution` の項目は `note` 列に理由と承認者を書く。記録はPRのレビューと承認とともに Git に残る。

| 分類 | 基準 | 扱い |
|---|---|---|
| 通常 | 日常の行動・態度・好み（observation-domains.md の範囲） | 採用可 |
| 要注意 | 回答が健康状態・信条・社会的身分を強く推測させうる | 表現を変えるか不採用。研究責任者の承認が必要 |
| 要配慮個人情報に該当しうる | 病歴、障害、診療情報、信条、犯罪歴など | **採用しない**（observation-domains.md §5 の対象外に該当） |

## 3. 仮名化

1. 研究のための解析は、`isobath_pipeline` ロールで `analysis` スキーマのみを読む。このビューは A・B を含まず、研究参加への同意が有効な利用者（`analysis.research_participants`）のデータだけを返す（design.md §4.5）。
2. `pseudo_id` はランダムな UUID であり、メールアドレス等から導出しない。
3. 解析結果・中間ファイルに `pseudo_id` 以外の識別子を含めない。
4. 研究者は**原則としてメールアドレスを閲覧しない**。

## 4. アクセス権

| 主体 | A 本人識別情報 | B 対応表 | C 仮名化研究データ | D 集計データ | 手段 |
|---|---|---|---|---|---|
| 利用者本人 | 本人分のみ | — | 本人分のみ（API経由） | 閲覧 | FastAPI + RLS |
| API（`isobath_api`） | — | 本人分のみ（RLS） | 本人分のみ（RLS） | — | `SET LOCAL ROLE authenticated` |
| 解析担当（`isobath_pipeline`） | 不可 | 不可 | 全件（読み取りのみ） | 作成 | `analysis` スキーマ |
| 研究責任者 | 請求対応時のみ | 請求対応・調査時のみ | 可 | 可 | Supabase ダッシュボード（MFA必須） |
| 開発・運用担当 | 障害対応時のみ、記録を残す | 同左 | 同左 | 可 | 同上 |

1. B へのアクセスは、本人からの請求対応とインシデント調査に限る。アクセスした場合は日時・目的・実施者を記録する。
2. Supabase のダッシュボード、Render、Cloudflare のアカウントは MFA を必須とし、権限を持つ者を【要記入】名以内に限る。
3. `service_role` 相当の資格情報は通常の API に使用しない（design.md D-6）。

## 5. 保存期間

公開版「データの保存と削除」の表に従う。内部的な実装は次のとおり。

| データ | 実装 |
|---|---|
| アカウント削除 | `app.delete_me()` が `auth.users` を削除し、`app.*` はカスケード削除。`deletion_tombstones` に `pseudo_id` を記録 |
| tombstone | 削除からバックアップの最長保持期間が経過した時点で削除（復元され得る複製が残る期間と一致させる） |
| 同意履歴（`consent_events`） | アカウント削除時に `user_id` を null にし、仮名IDと履歴のみ【要記入】年保存 |
| 解析用の抽出データ | パイプライン実行後に削除。残す場合は次回実行前に tombstone で除外（requirements ST-CHT-04） |
| バックアップ | Supabase の保持期間【要記入：プランにより異なる】。バックアップから復元した場合は、復元直後に tombstone と照合して削除済み利用者のデータを再削除し、研究参加を撤回した利用者の状態も同意履歴から復元されることを確認する |
| アクセスログ | Render / Cloudflare の保持期間【要記入】 |

## 6. 解析用データの持ち出し

1. `analysis` からの抽出データは、暗号化されたストレージ上でのみ扱う。【要記入】
2. 共同研究者等へ提供する場合は、研究責任者の承認のうえ、原則として集計データ（D）とする。個票（C）を提供する場合は【要法務確認：第三者提供・共同利用の整理】。

## 7. 研究終了後の扱い

1. 研究終了とその後の手順・時期を、事前に本サービス上で告知する。
2. 研究終了時に、新規の回答受付を停止する。
3. 【要記入：対応表（B）を破棄する時期】。B の破棄は事前に告知する。破棄後は撤回・削除の請求に応じられなくなるため、公開文書（research.md §12、data-retention.md）と整合させる。
4. B を破棄しても C は直ちに個人データでなくなるとは限らない。保存期間の満了時に C を削除し、D のみを残す。

## 8. 改訂時の除外の定義

研究参加の撤回またはアカウント削除があった利用者について、「除外する」とは、次のことをいう。

1. 次の日次バッチ（01:00 JST の締め）で生成する海図の密度・集計に含めない（`isobath.nightly` は、研究の同意が有効な利用者の現在地だけを集計する）。
2. 次回のモデル改訂では、除外後の `analysis.responses` のみから EFA・PCA・GMM 等を推定し直す。
3. 前版から引き継ぐのは、座標の向きをそろえるための前版の集計済みパラメータ（因子負荷等）のみとし、個人単位のデータや中間集計は引き継がない。

## 9. 公表時の統計情報化

1. 公表物（人格海図、論文、統計資料）には集計値のみを用いる。
2. 人数が k 人未満の区分は集約または非表示にする（requirements FR-CHT-04。k は Q-06 で決定）。
3. 海図の改訂時は、前版との差分（セル単位の人数の増減など）から、特定の個人の追加・撤回が推測されないことを確認する。
4. 個人の回答パターンや、少数の回答者の組み合わせから個人が推測されうる表・図を公表しない。
5. 自由記述は収集しない。
6. 公表前に研究責任者が上記を確認する。

## 10. 再識別の禁止

C または D から特定の個人を識別しようとする行為を禁止する。
