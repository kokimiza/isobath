# 非同期処理・UX走査（2026-09-24）

## 結論と範囲

`async/await` は使われているが、画面の寿命、通信の寿命、操作の完了状態が統一されていない。
待機表示だけを追加しても、遅れて届く応答による画面遷移、重複完了、取得済みデータの消失は防げない。

対象は認証・登録・同意・ヘッダー遷移・海図・プロフィール・航跡・設定・回答・通信共通処理。
ホームと運航状況も確認した。前ターンのプロフィール取得分離・遷移待機表示を含むローカル作業ツリーを対象とする。
本番DBや実利用者の認証情報は使用していない。

ローカルの本番ビルドをPlaywrightで起動し、ダミーAPIの遅延と失敗を制御した。
下記4件を再現確認した。これは**不具合の再現テストが成功した**という意味で、修正済みという意味ではない。
今回の走査ではサービスのコードを追加変更していない。

## 実行で確認した問題

### A1 / P1：離れた回答画面が、移動先を上書きする

- 場所：`src/lib/components/SurveyRunner.svelte:41`、`:57`。
- 再現：回答開始POSTを保留 → ヘッダーから海図へ移動 → 古いPOSTを `initial_exists` で完了。
- 結果：海図から意図せず `/profile` へ遷移する。
- 原因：アンマウント後も `refuse()` 内の `goto()` が実行される。
- 対応：画面ごとの世代番号／有効フラグを持ち、破棄された画面は状態・遷移を変更しない。
  読取通信はAbortSignalで中断。書込通信は、クライアントの中断をサーバの取消しと誤認しない。
- 合格条件：移動前のどの応答・拒否・例外が返っても、移動先URLと画面を維持する。

### A2 / P1：回答後の次ページ取得・完了処理が二重に走る

- 場所：`src/lib/components/SurveyRunner.svelte:105`、`:118`、`:161`、`:174`。
- 再現：最後の回答を送信 → 次ページGETを保留 → タブ非表示イベント → GETを解放。
- 結果：次ページGETが2回、完了POSTが2回発生する。
- 原因：`syncing=false` に戻した後で `nextPage()` をawaitする。再度の `sync(true)` が入り込める。
- 対応：送信・次ページ取得・完了までを1つの実行中Promise／状態機械で直列化する。
  完了POSTには専用の重複防止と、応答喪失時の完了状態照合も必要。
- サーバ側の補足：`app/isobath/routers/surveys.py` の完了APIは開いているセッションを前提とする。
  二重POSTで成功が保証される契約ではなく、片方の失敗が完了画面をエラーへ変える可能性がある。
  このサーバ競合の最終表示までは今回実測していない。
- 合格条件：連打・タブ切替・通信遅延を組み合わせても完了操作は1回。応答喪失後も完了済みを回復できる。

### A3 / P1：補助的な海図取得の失敗で、取得済みの航跡が消える

- 場所：`src/routes/(client)/(app)/journey/+page.svelte:27`、`:55`。
- 再現：履歴APIは成功、海図APIだけ500。
- 結果：履歴・位置が取得済みでも、エラーだけの画面になる。
- 原因：履歴と海図が同じ例外処理・同じ最上位エラー表示を共有している。
- 対応：履歴を主データとして表示し続け、海図の失敗は該当箇所に表示する。海図だけ再試行できるようにする。
- 合格条件：海図404・500・タイムアウトのいずれでも履歴と本人の位置を利用できる。

### A4 / P2：2ページ目が遅いだけで、取得済みの1ページ目も表示されない

- 場所：`src/routes/(client)/(app)/journey/+page.svelte:9`、`:19`、`:25`。
- 再現：履歴の1ページ目を即時返却、2ページ目を保留。
- 結果：最初の履歴があるのに、画面は読み込み中のまま。
- 原因：最大10ページを逐次取得し終わるまで `snapshots` に代入しない。
- 対応：最初の50件で即表示し、次ページは「さらに読み込む」。追加取得が失敗しても既存項目を残す。
- 合格条件：2ページ目の失敗・遅延が、1ページ目の閲覧を妨げない。

## コードから確認した問題

### A5 / P2：海図ページの取得順序が不要な待ち時間を作る

- 場所：`src/routes/chart/+page.svelte:27`。
- `/meta` → `/chart/current` の順で待ち、最後に一括表示する。本人の位置は別通信で得られても最上位エラーに隠れる。
- 独立した取得を並行開始し、概要・集団海図・本人位置を個別の状態で表示する。
  一部成功を利用者へ返し、最初から全部揃うことを要求しない。

### A6 / P1：登録・同意・回答の初期取得や完了失敗から、画面内で復帰できない

- 場所：`auth/signup/+page.svelte:30`、`(app)/consent/+page.svelte:36`、
  `SurveyRunner.svelte:187`、`(app)/profile/+page.svelte` の主データ取得。
- 初期APIが失敗すると送信不能またはエラー表示となり、再取得ボタンがない。
  回答の「送信失敗」には再試行があるが、「次ページ取得」「完了」には同じ回復経路がない。
- 入力・回答を保持したまま、失敗した処理だけを再実行する。書込みの自動再送は冪等性と状態照合が必要。
- 合格条件：リロードせずに回復し、入力した値を再入力しなくてよい。

### A7 / P2：通信の待機・中断・エラー分類が統一されていない

- 場所：`src/lib/api.svelte.ts:177`、`:182`、`:198`、`:208`、`:251`、`src/lib/auth.svelte.ts:30`。
- アプリ側の90秒制限・遅延表示はfetchが対象。認証セッション取得と更新はその外にある。
  応答ヘッダー受信で遅延表示を終了するため、本文受信中でも表示が消える。
  呼出し元からAbortSignalを渡せず、読取通信を画面破棄時に止められない。
- すべての503を「測深の受付停止」と訳すため、読取・同意確認の障害でも誤った説明になる。
- セッション確認も含む操作単位で待機を管理し、取消し／期限超過／通信障害／認証失敗／業務エラーを区別する。
  `startAuth()` のPromise例外も処理する。認証ライブラリ内部の待機上限は今回監査していない。

### A8 / P1：ログアウトの失敗処理がなく、未送信下書きを先に消す

- 場所：`src/routes/(client)/(app)/settings/+page.svelte:35`。
- 下書き削除 → `signOut()` → 遷移の順で、処理中表示・例外処理・返されたerrorの検査がない。
  サインアウトに失敗しても下書きだけ失われる経路がある。
- 明示的なログアウト中状態を持ち、認証処理の結果を確認する。成功時の機密下書き削除は維持し、
  失敗時にログイン状態と保存状態が食い違わないよう設計する。

### A9 / P2：設定の失敗が別の操作のエラーとして見える

- 場所：`src/routes/(client)/(app)/settings/+page.svelte:16`、`:24`、`:97`。
- 研究参加情報の読み込み中は見出しだけ。取得・参加変更・削除で共通errorを使い、
  エラーは「アカウント削除」欄に出る。成功後も古いエラーを消さない。
- 読込・参加変更・削除・ログアウトを別状態にし、操作した場所に待機／結果／再試行を出す。

### A10 / P2：フォームは無効化されるだけで、処理中の内容が分からない

- 場所：`AuthMethods.svelte:64`、`:93`、`(app)/consent/+page.svelte:101`、`auth/signup/+page.svelte:82`。
- `busy` による無効化はあるが、ボタンの文言と処理中の通知が変わらない。
  signupの画面遷移にはbusyがなく、各ハンドラーにも実行中ガードが一貫していない。
- 「ログイン中」「同意を保存中」など操作に即した表示を使う。ボタン無効化に加え、
  ハンドラー入口でも重複実行を抑止する。

## 追加計測が必要な箇所

- `OceanChart3D.svelte:55` の等値面生成は同期処理。`:216` の全三角形の投影・ソートもメインスレッドで行う。
  requestAnimationFrameは実行時刻を揃えるだけで、計算を別スレッドに移すものではない。
  大きな実データ相当の格子・多数の海域でクリック遅延を計測し、必要なら等値面生成をWorkerへ移す。
  今回、これが本番のprofile無反応の原因だとは確認できていない。
- `draft.ts` は保存不可の例外を握りつぶす。回答自体は継続できるが、保存に失敗した場合の警告がない。
  保存不可・オフライン・画面離脱を組み合わせた回答保全テストが必要。

## 維持する仕組み

- 回答は先にローカル下書きへ記録し、5件単位で送るため、通常時に毎問の通信を待たない。
- 回答送信の単一実行ガード、`already_answered` 時の照合、未送信回答の手動再試行がある。
- 海図の本人取得には有効フラグがあり、古い応答を捨てる実装例が既にある。
- 直前のprofile修正は、海域取得とプロフィール本体の失敗を分離できている。
  この方式を航跡と海図ページへ適用する価値がある。
- 遷移待機のstatus表示、APIの遅延通知、書込ボタンのdisabledは基礎として維持する。

## 対応順序

1. **`impeccable harden`**：A1・A2・A8。古い画面による操作、重複完了、下書き消失を止める。
2. **`impeccable harden`**：A3・A6・A7・A9。読取の寿命管理、部分失敗、再試行、適切なエラー分類を共通化する。
3. **`impeccable optimize`**：A4・A5。最初の有用な内容を先に表示し、残りを並行／段階取得する。3Dは計測して判断する。
4. **`impeccable clarify` → `impeccable polish`**：A10。操作ごとの待機・保存・成功・失敗を、一貫した表示にする。

認証・同意確認は省略しない。保護データを先に見せる最適化はしない。
画面骨格と待機状況を早く示し、許可済みのデータだけを到着順に表示する。
